# Brief: LLM Bill Analysis + Toadie Rankings

**Status**: Ready to design  
**Date**: 2026-05-23  
**Verdict**: BUILD — two separable phases, phase 1 (rankings) is pure data work with no LLM dependency

---

## Problem

The site tracks votes but doesn't answer the most interesting questions:
- *Who are the biggest toadies overall?*
- *What does this bill actually do, in plain English?*
- *How aligned is each legislator with Trump's positions as a whole?*

Rankings require aggregating vote history. Bill summaries require understanding legislative text. LLM handles the second; pure math handles the first.

---

## Current Data

- **47 tracked events**, **11,367+ actions**, **532 subjects with vote history**
- Each action has: `subjectId`, `alignment` (pro/anti), `eventId`, `date`, `topic`, `chamber`
- Each subject has: `name`, `party`, `state`, `type` (Senator/Representative/Admin Official)
- Ranking math already validated:
  - Top toadies: Bill Cassidy, John Cornyn, Markwayne Mullin, Tommy Tuberville (100%, 24-26 votes each)
  - Bottom: Maxine Waters, Debbie Wasserman Schultz, Frederica Wilson (0%, ~20 votes each)
- Events have `description` and `sourceUrl` but no plain-English summary or explicit Trump policy signal

## Phase 1: Toadie Rankings (no LLM needed)

### Ranking model

Simple weighted alignment score per subject:

```
toadie_score = pro_votes / total_votes_on_tracked_events * 100
```

Nuances to handle:
- **Participation floor**: minimum 3 eligible votes to appear on rankings (avoids senators who only voted on 1 House bill — not applicable, but future-proof)
- **Chamber separation**: Senate and House rank separately (senators and reps don't vote on the same bills)
- **Party context**: show rank within party as well as overall — a Republican at 60% is very different from a Democrat at 60%
- **Missing votes**: abstentions/not-voting are excluded from denominator (already the case — "Not Voting" is stripped at ingestion)

### New data file: `rankings.json`

Generated by a script `generate_rankings.js`, run as part of the build or cron cycle:

```json
{
  "generated": "2026-05-23T...",
  "senate": [
    { "subjectId": "C000174", "name": "Bill Cassidy", "party": "Republican", "state": "LA",
      "score": 100.0, "pro": 26, "total": 26, "rank": 1, "partyRank": 1 }
  ],
  "house": [...],
  "lastUpdated": "2026-05-23"
}
```

### New page: `/toadies/rankings/`

- Two tabs: Senate / House
- Sortable by: score %, total votes, alphabetical, state, party
- Color-coded by score: deep red (100%) → white (50%) → deep blue (0%)
- Each row links to the subject's existing `/subjects/[id]/` page
- Show party rank alongside overall rank
- Optional: "Most Improved Toady" — score delta since first tracked vote (requires per-event scoring snapshots, defer to later)

## Phase 2: LLM Bill Analysis

### What the LLM does

For each tracked event, generate:
1. **Plain-English summary** (~2 sentences): what the bill actually does
2. **Trump alignment signal**: explicit statement of Trump's position and why a Yea/Nay vote aligns with it
3. **Tags**: policy keywords beyond the 3 current topics (e.g. "immigration", "tariffs", "LGBTQ", "environment")

### Input to the LLM per event

```
Title: H.R. 28: Protection of Women and Girls in Sports Act
Description: Voted [X] on H.R. 28: Protection of Women and Girls in Sports Act of 2025
Source: https://clerk.house.gov/Votes/202512
Topic: Social Issues
Pro-vote direction: Yea = aligned with Trump
```

Optionally: fetch the full bill text from congress.gov API (free, no key needed for basic lookups) and include a truncated summary in the prompt.

### Prompt design

```
You are a nonpartisan political analyst. Given the following congressional vote:

Title: {title}
What happened: {description}  
Topic area: {topic}
A "Yea" vote on this bill is considered alignment with Trump's position.

In 2 sentences, summarize what this legislation does in plain English.
Then in 1 sentence, explain why voting Yea aligns with Trump's stated positions.
Return JSON: { "summary": "...", "trump_signal": "...", "tags": ["tag1", "tag2"] }
```

### Ollama instance

- **Host**: `localhost:11434` — confirmed reachable, API responsive
- **GPU**: NVIDIA RTX 1000 Ada (6141MB VRAM) — present and driver-accessible (`/dev/nvidia0`)
- **GPU note**: ollama currently runs via OpenWebUI's process context with GPU access. Running `enrich_events.js` directly from the terminal may hit CPU instead of GPU depending on the calling user's environment. Workaround: run via the same user/context as ollama (root), or set `CUDA_VISIBLE_DEVICES=0` in the script environment.

### Recommended model: `mistral:7b-instruct` (already installed)

**Why this model:**
- Already installed at 4.4GB (Q4_K_M) — fits in 6GB VRAM with headroom
- Tested against a real bill prompt and produced clean, valid JSON on first attempt:
  ```json
  {
    "summary": "This bill prohibits transgender women and girls from competing in female sports categories in schools and colleges receiving federal funding.",
    "trump_signal": "Aligns with Trump's stance on gender issues, as he has expressed support for policies that limit the rights of transgender individuals.",
    "tags": ["Transgender Rights", "Sports", "Gender Policy"]
  }
  ```
- `qwen2.5:7b` (also installed, 4.5GB) is a viable alternative — slightly better at structured output, worth A/B testing

**Also installed (not recommended for this task):**
- `llama3.1:8b` — 4.9GB, good but no advantage over mistral for this task
- `nous-hermes2:latest` — 6.1GB, pushes VRAM limit uncomfortably
- `codellama:7b-instruct` — tuned for code, wrong fit
- `phi3:mini` — 2.2GB, would work for summaries but weaker political reasoning
- `all-minilm` — embedding model, useful for semantic similarity ranking (Phase 3 option)

### Ollama integration

- Script: `enrich_events.js` — reads `actions.json`, hits ollama HTTP API (`http://localhost:11434/api/generate`), writes enriched metadata to `src/data/events_meta.json`
- Runs on demand (not every cron cycle) — bill text doesn't change after passage
- Output is a separate file so it doesn't touch `actions.json`
- Processes only events missing from `events_meta.json` — safe to re-run incrementally
- Rate: ~5-10 seconds per event on GPU; 47 events = under 10 minutes total

### New `events_meta.json` shape

```json
{
  "2025-01-14-hr28-sports-act": {
    "summary": "Bans transgender women and girls from competing in female sports categories in schools and colleges receiving federal funding.",
    "trump_signal": "Trump has explicitly supported this ban as part of his platform opposing transgender participation in women's sports.",
    "tags": ["transgender", "education", "Title IX", "women's sports"],
    "enriched": "2026-05-23T10:00:00Z"
  }
}
```

### UI changes

- Event cards on feed: add summary blurb below title (replacing the current raw description)
- Event detail page: show summary + trump_signal + tags

## Phase 3: Composite Toady Score (combines phases 1 + 2)

Once events have LLM-generated Trump alignment signals, weight votes by confidence:

```
weighted_score = Σ (alignment_match * event_weight) / Σ event_weight
```

Where `event_weight` could be:
- 1.0 for high-confidence Trump-aligned votes (explicit Trump endorsement)
- 0.5 for inferred alignment (party-line but no explicit Trump statement)

Defer this until Phase 2 output is validated — the LLM signal needs to be audited before it affects scores.

## Risks

- **LLM accuracy**: Ollama/local models can hallucinate bill details. Summaries should be clearly labeled "AI-generated summary" and sourced back to official records. The `trump_signal` field especially needs human review before being treated as authoritative.
- **Ranking fairness**: Senators only vote on Senate bills; reps only vote on House bills. A senator who voted on all 16 Senate events is more comparable to other senators than to reps who had 31 House events. Keep chambers separate.
- **Model availability**: `enrich_events.js` should fail gracefully if ollama is unreachable — fall back to showing the raw description.
- **Re-enrichment**: When new events are added, only enrich new ones (check for existing key in `events_meta.json`).
